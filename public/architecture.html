Overview

What the product does

Most users don't know how to write effective AI prompts. Advanced Prompting solves this with a structured 3-step guided flow.
📝
1 · Describe
User types their need in plain language. Claude auto-fills structured fields.
→
💬
2 · Review
Claude shows what it understood. User confirms assumptions & fills gaps.
→
✅
3 · Results
Claude generates output with confidence levels. User validates & exports.
No prompt knowledge needed — plain English is enough
Validation before generation — Claude confirms intent first
Confidence-tagged output — uncertain sections flagged for review

Key principles

  • No database — all session state lives in the browser. Zero server-side storage.
  • No framework — pure HTML/CSS/JS. Zero build step, instant deploy.
  • Serverless functions — two Node.js lambdas proxy the Anthropic API.
  • JSON-first AI — assistant prefill forces valid JSON every time.

    • Data flow summary

    Data Flow

    End-to-end request pipeline

    1
    User describes task (Screen 1) Browser
    Plain text in paste zone → auto-fills goal, context, format, role, constraints fields. Stake level + model selected.
    2
    POST /claude-understand → parse intent Haiku 4.5 · ~1s
    Returns JSON: goal, ctx, fmt, role, con, stakes, interpretation (bullets), assumptions[], questions[]
    3
    User reviews + answers questions (Screen 2) Browser
    Confirms assumptions, answers gap-fill questions, optionally adds extra context. "Review updates" re-calls claude-understand with enriched context → questions drop to 0.
    4
    POST /claude-generate → produce result Sonnet 4.6 / Opus · 5–20s
    Returns JSON: outputs[] with title, body (HTML), badge (bv/br/bd), badgeText, reasonKey + reasons{}. Assistant prefill "{" guarantees JSON.
    5
    User validates, edits, locks, exports (Screen 3) Browser
    Accepts sections, inline-edits, re-runs unlocked sections, exports HTML/PDF/text.
    04 / 14
    Frontend

    Single-page architecture (no framework)

    Screen routing

    Three <div class="screen"> elements always in the DOM. Active screen toggled via .active CSS class. No URL routing needed — state is ephemeral.

    State object — CASES.merge

  • goal, ctx, fmt, role, con — task fields
  • interpretation, interpretationBullets — what Claude understood
  • assumptions[], questions[] — gap analysis cards
  • cardAnswers, cardSkipped, cardClarifications — user responses
  • outputs[], reasons{} — generated result sections
  • extraContext — user additions passed to generate

    • Right panel — context-aware

    Swaps content per screen: How it works on Describe, Why this step on Review, Review guide + thinking flow on Results.

    Task type detection

  • jobsearch — career/salary/role keywords → tiered output layout
  • prototype — html/ui/design/app keywords → HTML screen output
  • document — resume/write/draft keywords → section layout
  • generic — default → flexible sections
    • Detected client-side and sent to both serverless functions for specialized prompting.

    Export system

    Export as-is (blob download) or Polish & export (second Claude call). Prototype = multi-screen HTML with tab nav. Document = plain text or PDF-print.

    Backend — Function 1

    claude-understand — intent parser

    Modelclaude-haiku-4-5-20251001
    Max tokens1 024
    Avg latency~0.8 – 1.5 s
    Called whenUser clicks "Understand" or "Check"
    Re-called whenUser clicks "Review updates" on Screen 2

    Output JSON schema

    {
      "goal": "1–3 sentence result",
      "ctx": "background info",
      "interpretation": "2–4 bullet sentences",
      "stakes": "low | med | high",
      "assumptions": [{"text":…, "risk":…}],
      "questions": [{"id":…, "q":…, "opts":[3]}]
    }

    Questions guidance (prompt rules)

  • Low stakes: 0 questions — just start
  • Med stakes: 0–3 questions (only genuine gaps)
  • High stakes: 1–5 questions (blockers only)
  • Each question has exactly 3 options
  • On re-parse with answers: question count drops significantly

    • Re-parse enrichment (Review updates)

    Combines: original text + answered Q&A + extra user context → sends to Haiku again.

    Result: fresh interpretation, updated assumptions, reduced questions. Preserved answers for question IDs that remain.

    Task-type routing → specialised prompts

  • prototype — split into 2–3 HTML screen snippets (self-contained divs)
  • jobsearch — roles/sectors + strategy + unknowns sections
  • document — 2–3 logical sections, HTML body content
  • generic — flexible 2–3 sections

    Each output section carries: title, body (HTML), badge (bv/br/bd), badgeText, reasonKey.

    AI Design

    Two-phase AI pipeline

    Phase 1 — Parse (claude-understand)
    ModelHaiku 4.5
    PurposeUnderstand intent
    Tokens≤ 1 024
    Latency< 2 s
    Cheap, fast. Run on every keystroke/re-parse. Fills Screen 2 interpretation + questions.
    →
    confirmed
    intent JSON
    Phase 2 — Generate (claude-generate)
    ModelSonnet 4.6 / Opus 4.8
    PurposeProduce final output
    Tokens≤ 4 096
    Latency5 – 20 s
    Runs once per "Run Next" or "Re-run". User chooses model. Locked sections never re-sent.

    Separation of concerns

    Parse ≠ Generate. Haiku does the cheap validation; the expensive model only runs when the user is confident.

    JSON contract enforcement

    System prompt mandates JSON. Assistant prefill { eliminates any conversational preamble. Three-pass extractJSON fallback handles minor malformations.

    Re-run with lock

    User can lock accepted sections. Re-run sends the same prompt to generate only unlocked sections. Locked content is never touched.

    State Design

    Browser-only state machine

    Why no backend database?

  • Tasks are ephemeral — one session, one result
  • No user accounts needed for the prototype flow
  • Zero latency on state reads — all in memory
  • Privacy — nothing is persisted server-side

    • State transitions

    empty → user types
    parsing → Haiku call in flight
    parsed → fields filled, Screen 2 ready
    reviewing → user answering cards
    confirmed → all cards answered
    generating → Sonnet call in flight
    done → output on Screen 3

    CASES.merge — key fields

    goal · ctx · fmt · role · con · stakes
    interpretation · interpretationBullets[]
    assumptions[] · questions[]
    cardAnswers{} · cardSkipped(Set)
    cardClarifications{} · extraContext
    outputs[] · reasons{}

    Card answer persistence

    Answers are stored in cardAnswers (keyed by question ID). On Screen 2 re-render (doReviewAgain), answered cards are restored by _restoreCardState() and then hidden — they appear in the understanding summary instead.
    09 / 14
    Output Design

    Confidence badge system

    ✓
    bv — High confidence
    Factual, straightforward. Claude is sure. Accept without hesitation.
    ⚠
    br — Review recommended
    Style choices made, interpretation involved. Worth checking.
    ⚠️
    bd — Needs validation
    Numbers, facts, legal/financial items. Claude is not 100% sure. Must verify.

    Rendering — bv sections

    White background, blue border badge. Default "Accept 🔒" button. User locks and moves on.

    Rendering — br sections

    White background, amber badge. "Edit ✏" + "Accept" buttons. Encourage a read-through before accepting.

    Rendering — bd sections

    Red tinted background. Grouped under "Needs your validation" header at bottom. "Edit" only — must correct before accepting.
    Why this matters:
    Users are shown EXACTLY where to focus attention. High-confidence content is not cluttered with caveats. Uncertain content is visually distinct and cannot be accidentally accepted without review.

    Design Decisions

    Why we built it this way

    Two-API pipeline (not one big call)

    Parsing and generating are different problems. Haiku (cheap + fast) handles intent parsing with 100% reliability. Sonnet/Opus (expensive) only runs once the user has confirmed intent — no wasted tokens on misunderstood requests.

    Assistant prefill " { " for JSON

    JSON-only instructions in a system prompt can be ignored when Claude senses a conversational context. Prefilling the assistant turn with { makes it architecturally impossible for Claude to start with prose — the token is already committed.

    No database

    Sessions are single-use. Persisting them server-side adds auth, GDPR surface, and infra cost for zero user benefit. Browser state is wiped on tab close — which is intentional for a prompt-drafting tool.

    Task-type specialisation

    A generic "write stuff" prompt produces mediocre results. Prototype tasks need HTML screen divs; job search tasks need tiered salary analysis; document tasks need logical sections. Routing to specialised prompts dramatically improves output quality.

    Validate before generate

    Screen 2 exists purely to surface Claude's assumptions and fill information gaps BEFORE burning tokens on full generation. The cost of a re-parse (Haiku, <$0.001) is negligible compared to a wrong Sonnet generation.

    Confidence-first output

    Showing everything as "here's your answer" is dangerous for high-stakes tasks. The bv/br/bd badge system forces Claude to self-assess and directs user attention to exactly where human judgment is needed.
